Ferramentas de busca em Python podem ser auditadas, corrigidas e 3x mais rápidas

A maioria das ferramentas de busca para o Bitcoin Puzzle circula como binário fechado — e ninguém sabe o que roda dentro delas. Nesta análise, abrimos o repositório, encontramos falhas reais de segurança e reescrevemos tudo em Python puro, sem nenhuma dependência externa.

O repositório Bitcoin do @CanalQb reúne três ferramentas: uma busca pseudoaleatória de chaves privadas, uma busca baseada em endomorfismo da secp256k1 e um snapshot da blockchain para análise. O problema imediato: tudo era distribuído como executável compilado, sem código-fonte. Para um projeto que lida com criptografia de curva elíptica, isso é o mesmo que entregar um cofre sem mostrar a fechadura.

Então o desafio ficou claro: auditar o que existe, corrigir o que estava errado, e devolver para a comunidade uma versão aberta, segura e eficiente. Foi exatamente o que fizemos — e o resultado está neste post, com comandos reais, logs reais e números de desempenho medidos na prática.

O que o Bitcoin Puzzle faz e por que ele é um laboratório perfeito

O "Bitcoin Puzzle Transaction" é um desafio público que travou BTC em 160 endereços cujas chaves privadas estão em intervalos conhecidos: o puzzle N usa o intervalo de 2^(N-1) até 2^N - 1. Não há nenhuma vulnerabilidade na criptografia — é um teste de paciência, eficiência e sorte.

Os puzzles 1 a 50 já foram resolvidos publicamente; o puzzle 66, por exemplo, caiu em janeiro de 2024 e seus 6,6 BTC foram sacados. Os puzzles 67 em diante continuam de pé, com valores crescentes. Para um estudante de criptografia, esse cenário é ideal: você pode validar uma implementação completa (curva elíptica, hashing, encoding, endereços) contra dados reais e conhecidos, sem precisar de infraestrutura de verdade.

Aqui no @CanalQb, validamos cada função da nova implementação contra os endereços reais dos puzzles 1 a 19, cujas chaves privadas são públicas. Se a sua ferramenta deriva o endereço correto para a chave 224 do puzzle 8, a sua matemática está certa — e isso é verificável em segundos.

Quais falhas de segurança foram encontradas na versão original

Encontramos 2 falhas de segurança de nível alto e 1 de nível crítico na cadeia original. Nenhuma delas era um bug de matemática — eram decisões de arquitetura.

Falha 1 — semente previsível (HIGH): a busca pseudoaleatória original usava o endereço MAC da placa de rede como semente do gerador de números aleatórios. O MAC é um identificador público, visível em qualquer rede local, e previsível. Pior: duas execuções na mesma máquina produzem a mesma sequência, desperdiçando trabalho. A correção foi usar o CSPRNG do sistema operacional via secrets.randbelow() — entropia real, sem exposição de identidade do dispositivo.

Falha 2 — banco de dados remoto (HIGH): as ferramentas originais dependiam de um PostgreSQL remoto com credenciais para obter intervalos e endereços-alvo. Isso significa credenciais em arquivo de configuração, exposição de dados de uso e um ponto único de falha. A correção foi eliminar completamente o banco remoto: os dados dos 160 puzzles agora vivem em um arquivo JSON local versionado (data/puzzles.json), e o snapshot usa SQLite local.

Falha 3 — token exposto (CRITICAL): durante o processo de sincronização, um token de acesso do GitHub foi utilizado na URL do repositório remoto e ficou gravado no config local do clone. Isso foi classificado como exposição de credencial, a URL foi sanitizada após o push e a recomendação é rotacionar o token. Nunca coloque tokens em URLs, código ou documentação — use variáveis de ambiente ou o GitHub CLI autenticado.

Além das falhas, encontramos e corrigimos um bug real de implementação: a função de validação de endereços-alvo usava a decodificação Base58 crua (25 bytes, incluindo checksum) em vez da Base58Check (21 bytes de payload). Resultado: qualquer endereço-alvo era rejeitado. O teste automatizado cobre essa regressão para sempre.

Análise técnica dos executáveis originais

Os três executáveis nas pastas Puzzle_Random_Search/, endomorph_puzzle/ e Snapshot/ foram preservados intactos, mas receberam uma análise técnica detalhada. Os resultados revelam uma estrutura que confirma — e aprofunda — o que os readmes indicavam.

Linguagem: os três binários são PE32+ x86-64 compilados em Swift (marcadores __swift_1 e __swift_2 no binário), com o runtime da linguagem embutido — o que explica o tamanho de 7,6 MB a 15,5 MB para funcionalidades que em Python puro ocupam ~50 KB de código.

Banco remoto confirmado: a string 5432 (porta padrão do PostgreSQL) e prefixos pg_ aparecem nos três executáveis, confirmando a dependência de um banco de dados remoto com credenciais. As strings de conexão (host, usuário, senha) não estão em texto claro — provavelmente ofuscadas ou criptografadas no recurso .rsrc.

Recurso .rsrc gigante: a seção de recursos (.rsrc) ocupa de 7,4 MB a 15,3 MB em cada executável — mais de 95% do tamanho total. O código (.text) é de apenas ~116 KB. Isso significa que os dados (intervalos, endereços, possivelmente um banco SQLite embutido) estão armazenados como recurso Windows. A versão Python substitui isso por um arquivo JSON de 37 KB.

Nome interno do projeto: o assembly manifest dos três binários registra o nome "Mini" version="1.0.0.0" — um detalhe de nomenclatura que não aparece nos readmes.

O SHA-256 de cada binário foi registrado no ANALYSIS.md para referência e auditoria futura. Nenhum binário foi executado, modificado ou desmontado além da inspeção estática de cabeçalhos e strings.

Como a reescrita em Python reduz o consumo de hardware

O objetivo não era só tornar o programa mais rápido — era obter o melhor equilíbrio entre CPU, RAM, disco e energia. A versão em Python puro ataca isso em cinco frentes.

Zero dependências: nada de pip install, nada de ambiente virtual, nada de bibliotecas compiladas. A implementação usa apenas a biblioteca padrão: hashlib para SHA-256/RIPEMD-160, secrets para entropia, sqlite3 para o banco local. Menos dependências significa menos memória, menos disco e menos superfície de ataque na cadeia de suprimentos.

Endomorfismo GLV: a secp256k1 tem uma propriedade algébrica especial: as constantes beta e lambda permitem transformar um ponto da curva em outros dois relacionados, que correspondem a chaves multiplicadas por lambda e lambda². Com isso, uma única multiplicação escalar gera 3 chaves candidatas. É um ganho de até 3x sem gastar energia extra — a matemática faz o trabalho.

Comparação por hash: em vez de converter cada chave candidata para o endereço Base58 completo (caro), a busca compara o hash160 do ponto diretamente contra um conjunto pré-computado de alvos. A codificação Base58 só acontece quando há uma correspondência — economia de CPU em todos os casos sem sucesso.

Arquitetura Jacobiana: a multiplicação escalar usa coordenadas Jacobianas, que eliminam as inversões modulares dentro do laço principal — apenas uma inversão no final. Isso reduz drasticamente o custo por multiplicação em comparação com a implementação ingênua em coordenadas afim.

Paralelismo sob demanda: o padrão é 1 processo (menor consumo de energia e temperatura). Se o usuário quiser, --workers N escala para quantos núcleos estiverem disponíveis — mas nunca mais do que o necessário.

O resultado medido no nosso hardware: ~7.900 chaves/s no modo endomorfismo com um único processo Python puro. Não é um recorde — implementações em C chegam a milhões —, mas é honesto, auditável e custa literalmente zero de configuração.

Passo a passo: instalar e rodar em menos de 1 minuto

O processo completo tem 5 etapas e nenhuma depende de instalação de pacotes. Abaixo, cada passo com o comando exato, o que ele faz, por que é necessário, o resultado esperado e o erro mais comum.

Passo 1 — clonar o repositório

git clone https://github.com/canalqb/Bitcoin.git
cd Bitcoin

Esse passo baixa o projeto para a sua máquina e entra na pasta. É necessário porque todos os comandos seguintes assumem que você está dentro do diretório Bitcoin. Quando funcionar, você verá a mensagem Cloning into 'Bitcoin'... e o prompt voltará.

Erro comum: se o seu git pedir autenticação, o repositório pode estar privado no seu acesso — confirme com o GitHub CLI (gh auth login) antes de clonar.

Passo 2 — gerar os dados dos puzzles

python tools/seed_puzzles.py

Esse script gera o arquivo data/puzzles.json com os 160 intervalos e endereços oficiais do desafio. Ele é necessário porque a busca precisa saber o intervalo de cada puzzle e qual endereço procurar. Quando funcionar, a saída será: [ok] data\puzzles.json gerado com 160 puzzles.

Erro comum: se o Python não for reconhecido, instale o Python 3.8+ e marque a opção "Add to PATH" durante a instalação.

Passo 3 — verificar a implementação (recomendado)

python tools/selftest.py

O selftest valida a criptografia contra vetores reais: os endereços dos puzzles 1 a 19, o vetor oficial BIP-173 (bech32), as propriedades do endomorfismo GLV e uma busca de integração nos puzzles 1 e 8. Ele é necessário porque confirma que a sua cópia está gerando endereços corretos antes de você confiar nela. Quando funcionar, a última linha será TODOS OS TESTES PASSARAM.

Erro comum: se algum teste falhar, o código foi alterado ou o Python é muito antigo — atualize para 3.11+ e rode novamente.

Passo 4 — encontrar a chave de um puzzle já resolvido (demo)

python tools/puzzle_search.py --puzzle 8 --mode sequential

O puzzle 8 tem a chave 224 (hex 0xe0), dentro do intervalo 128 a 255. O modo sequential percorre o intervalo em ordem e encontra em segundos. Esse passo é necessário para você entender a saída da ferramenta com um caso garantido, antes de tentar qualquer coisa maior. Quando funcionar, você verá:

=== CHAVE ENCONTRADA ===
chave (hex) : 0xe0
chave (dec) : 224
endereco : 1M92tSqNmQLYw33fuBvjmeadirh1ysMBxK
WIF : KwDiBf89QgGbjEhKnhXJuH7LrciVrZi3qYjgd9M7rFU...

Passo 5 — buscar um puzzle não resolvido com endomorfismo

python tools/puzzle_search.py --puzzle 66 --limit 100000

O modo padrão é endomorph, que testa 3 chaves por operação. O --limit impede que a busca rode para sempre — 100 mil chaves são suficientes para medir velocidade sem comprometer o hardware. É necessário porque o espaço do puzzle 66 tem 2^65 chaves: sem limite, a busca seria inútil e gastaria energia à toa. Quando funcionar, você verá a barra de progresso no terminal e, ao fim, o resumo de chaves testadas e velocidade.

Erro comum: "Nao encontrado" em um puzzle resolvido acontece quando você usa o modo random em um intervalo pequeno — o sorteio não garante cobertura. Use sequential para intervalos pequenos.

Snapshot de saldos sem baixar a blockchain inteira

A ferramenta Snapshot original baixava o estado completo da blockchain para um banco local — algo que consome dezenas de gigabytes de disco e horas de processamento. A nova versão resolve o mesmo problema com uma fração do hardware: consulta a API pública e confiável da blockstream.info, respeitando limite de requisições, e armazena tudo em SQLite local.

python tools/snapshot_btc.py --all-puzzles

O comando acima consulta o saldo dos 160 endereços do puzzle, usa cache em SQLite (segundas execuções são instantâneas), e mostra o saldo total e o top 10. Para exportar em TSV para análise externa:

python tools/snapshot_btc.py --all-puzzles --export-tsv snapshot.tsv

Na prática, isso significa que monitorar se um puzzle foi resolvido (saldo zerado) vira um comando de 10 segundos, não uma operação de horas com um nó completo rodando.

Quais novos recursos foram adicionados além das correções

Além de corrigir o que existia, a versão 2.0 adiciona recursos que não existiam na versão original em binário.

  • 3 modos de busca: sequential (determinístico e resumível), random (CSPRNG) e endomorph (3x via GLV).
  • Resume automático: o progresso é salvo atomicamente em JSON; um Ctrl+C não perde o trabalho, e o modo sequential retoma exatamente de onde parou.
  • Benchmark local: --benchmark --limit N mede a velocidade da sua máquina sem tocar a rede.
  • Selftest com 17 verificações: baseado em vetores reais e propriedades algébricas da curva.
  • Multiprocessamento opcional: --workers N para quem quiser usar mais núcleos; default de 1 processo.
  • Endereço P2WPKH (bech32): além do P2PKH usado nos puzzles, a biblioteca gera endereços segwit válidos.

Como validar se o seu hardware está sendo usado de forma eficiente

Três sinais indicam que a ferramenta está consumindo o mínimo necessário: a velocidade se mantém estável (sem picos de pausa que indicariam garbage collection excessivo ou contenção de I/O), a temperatura não sobe com o modo padrão de 1 processo, e o arquivo de resume é atualizado a cada 10 segundos sem travar a busca. Para medir na sua máquina:

python tools/puzzle_search.py --benchmark --limit 10000

O benchmark reporta chaves/s e tempo total. Se você quiser mais velocidade, --workers escala linearmente até o número de núcleos físicos — mas lembre-se: mais processos = mais energia. O equilíbrio certo depende do seu objetivo.

Perguntas frequentes sobre as ferramentas Bitcoin Puzzle

É seguro rodar esta ferramenta na minha máquina?
Sim, com ressalvas. O código é 100% aberto e usa apenas a biblioteca padrão do Python, sem dependências de terceiros — o que elimina o risco de cadeia de suprimentos. Nenhuma credencial é necessária e nenhum dado é enviado para a rede (exceto o snapshot, que consulta a API pública blockstream.info por HTTPS). O único dado sensível gerado é a chave privada quando a busca encontra uma correspondência — e ela fica apenas no seu terminal, com salvamento opcional em arquivo local ignorado pelo git. Como qualquer ferramenta de criptografia, rode primeiro o selftest.py para confirmar que a sua cópia está íntegra.
Por que o endomorfismo testa 3 chaves por operação?
A curva secp256k1 tem uma propriedade chamada endomorfismo GLV. Existem duas constantes especiais, beta (no corpo do campo) e lambda (no corpo da ordem), tais que, se você multiplicar a coordenada x de um ponto por beta, o resultado é um ponto válido da curva que corresponde à chave multiplicada por lambda. Aplicando duas vezes, você obtém um terceiro ponto, correspondente a lambda². Como beta³ ≡ 1 e lambda³ ≡ 1, o ciclo se fecha. Então, para cada chave k sorteada, a ferramenta testa k, k·lambda e k·lambda² — três endereços com o custo de uma única multiplicação escalar. O selftest valida essas identidades algebricamente (mul(lambda) == phi(G)), garantindo que a aceleração não quebrou a matemática.
Por que usar MAC address como semente era um problema de segurança?
O endereço MAC é um identificador fixo, público e previsível da placa de rede. Usá-lo como semente de um gerador pseudoaleatório tem três consequências graves: primeiro, qualquer observador em uma rede local pode ver o MAC e reproduzir a sequência de chaves geradas, eliminando o fator "aleatório" da busca; segundo, o MAC vaza identidade do dispositivo — uma pegada digital desnecessária; terceiro, a mesma máquina sempre gera a mesma sequência, então reiniciar a busca repete trabalho em vez de explorar o espaço. A substituição pelo secrets do Python usa o CSPRNG do sistema operacional (no Windows, o CryptGenRandom; no Linux, /dev/urandom), que tem entropia real e não expõe nenhum identificador.
A busca em Python consegue resolver um puzzle de 66 bits?
Estatisticamente, não em tempo útil — e é importante ser honesto sobre isso. O espaço do puzzle 66 tem aproximadamente 2^65 chaves. A nossa implementação mede cerca de 7.900 chaves/s por processo, ou seja, cerca de 6,8x10^8 chaves/dia. Para percorrer 2^65 chaves, seriam necessários algo em torno de 1,7x10^10 dias de um único processo. Implementações em C com otimização extrema e uso de GPU chegam a bilhões de chaves/s, e mesmo assim o puzzle 66 levou anos para cair. O valor desta ferramenta é didático: ela demonstra o algoritmo completo, é verificável contra puzzles resolvidos e serve de base de estudo — não é uma máquina de mineração. O modo sequential resolve os puzzles 1 a 50 em segundos, o que é um ótimo banco de testes.
O que mudou em relação à versão original em binário?
Tudo o que era fechado virou aberto e auditável. A versão original distribuía três executáveis Windows/Linux sem código-fonte, dependia de um PostgreSQL remoto e usava MAC address como semente. A versão 2.0 substitui os três binários por código Python puro (stdlib), com dados locais em JSON/SQLite, CSPRNG, endomorfismo GLV validado, resume automático, benchmark e um selftest de 17 verificações. Os binários originais foram preservados nas pastas de referência para comparação e estudos de engenharia reversa. A compatibilidade não é a mesma — a versão Python exige Python 3.8+ instalado —, mas o custo de instalação é zero dependências.
Como faço para contribuir com o projeto?
O fluxo padrão de código aberto: faça um fork do repositório, crie um branch descritivo, implemente a melhoria, garanta que python tools/selftest.py passe 100%, e abra um Pull Request com uma descrição clara do problema resolvido. Áreas que mais precisam de ajuda: implementações mais rápidas da multiplicação escalar (ex.: wNAF), testes adicionais de vetores, e melhorias no snapshot (novas fontes de dados com fallback). Antes de qualquer mudança criptográfica, leia o SECURITY.md — alterar a matemática para "ganhar desempenho" é exatamente o tipo de mudança que pode introduzir um bug sutil na geração de endereços.
